# Отчёт о производительности

## Как измерялось

* **Инструмент:** Lighthouse 13.4.1, headless Chromium 141, скрипт
  `scripts/lighthouse-audit.mjs`.
* **Сборка:** production (`pnpm build` + `pnpm start`), не dev-сервер.
* **Данные:** демонстрационный контент из `pnpm seed` (4 опубликованных кейса).
* **Профили:** mobile — стандартный профиль Lighthouse (390 × 844, DPR 2,
  замедление процессора 4×, эмуляция мобильной сети); desktop — 1440 × 900,
  RTT 40 мс, 10 Мбит/с, без замедления процессора.
* **Сырые отчёты:** `research/lighthouse/*.json`, сводка —
  `research/lighthouse/summary.json`.

**Важное замечание о среде.** Измерения выполнены на локальном сервере
без CDN и без сетевой задержки до реального пользователя, на программном
рендерере (SwiftShader вместо GPU). Абсолютные значения на боевом хостинге
будут отличаться; относительные выводы и найденные проблемы — нет.

## Что было найдено и исправлено измерением

Все четыре проблемы обнаружены Lighthouse, а не предположены.

### 1. CLS 0.33 на `/cases`

**Было:** 0.329 (mobile и desktop). Culprit по данным аудита — сдвиг `<footer>`.

**Причина:** список кейсов рендерился клиентским компонентом, который через
`useSearchParams` выводил себя из SSR. Сервер отдавал заглушку, реальный
список подставлялся после гидратации, страница «прыгала».

**Исправление:** `/cases` переведена на серверную фильтрацию по `searchParams`,
фильтры стали обычными ссылками. Побочные выигрыши: фильтрация работает без
JavaScript (покрыто E2E-тестом), меньше клиентского JS, лучше индексация.

**Стало:** CLS = 0, desktop `/cases` — 100.

### 2. Недостаточный контраст текста

**Было:** аудит `color-contrast` не проходил, Accessibility 94–95.

**Причина:** `--gm-steel` = `#6b7280` на `#0b0c0e` давал 4.1:1 при требуемых 4.5:1.
Тот же токен применялся и на светлых секциях, где давал ~3:1.

**Исправление:** `--gm-steel` → `#868d99` (5.6:1 на тёмном); для светлых секций
введён отдельный `--fg-subtle: #5f6672` (5.4:1 на бумаге).

**Стало:** Accessibility 100.

### 3. Пропуск уровня заголовков

**Было:** аудит `heading-order` не проходил на `/` и `/cases`.

**Причина:** на `/cases` за `h1` сразу шли `h3` карточек; в блоке
позиционирования на главной надзаголовок был `<p>`, а принципы — `h3`.

**Исправление:** у `CaseCard` появился настраиваемый уровень заголовка
(`h2` в списке кейсов, `h3` внутри секций со своим `h2`); надзаголовок блока
позиционирования стал `h2`.

### 4. LCP 5.6 с и TBT 990 мс на мобильной главной

**Было:** Performance 57, LCP 5.6 с, TBT 990 мс.

**Причины и исправления:**

1. Постер первого экрана был CSS-фоном внутри клиентского компонента: браузер
   узнавал о нём только после загрузки бандла. → Постер вынесен в серверный
   `Hero` и выводится через `next/image` с `priority`.
2. Сцена загружалась по `requestIdleCallback` с таймаутом 1200 мс, срабатывая
   в разгар загрузки. → Загрузка отложена до события `load` **и** следующего
   простоя.
3. На мобильных устройствах разбор three.js занимал ~2 с процессорного времени
   ради эффекта, у которого на touch нет половины смысла (нет курсора). →
   Сцена запускается на touch-устройствах только при ≥ 6 ядрах и ≥ 4 ГБ памяти;
   на остальных остаётся постер, отрендеренный из этой же сцены.

**Стало:** Performance 90, LCP 3.6 с, TBT 60 мс.

## Остающиеся ограничения

### desktop `/` — 87, TBT 300 мс

Это стоимость 3D-сцены: разбор и инициализация three.js занимают ~300 мс
процессорного времени после полной загрузки страницы. Сцена уже:

* грузится динамически (`ssr: false`) и не входит в основной бандл;
* стартует после `load` и простоя, то есть **после** LCP (0.7 с) и FCP (0.3 с);
* останавливается вне вьюпорта и при скрытой вкладке;
* ограничивает DPR (1.25–1.75) и снижает качество при просадке кадров.

Дальнейшее снижение возможно только отказом от реалтайм-сцены. Это осознанный
компромисс: сцена — носитель бренда, и её цена вынесена за пределы первичной
загрузки. Все остальные страницы, где сцены нет, дают 95–100.

### LCP 2.9–3.6 с на мобильном профиле

Профиль Lighthouse эмулирует медленную сеть без CDN. LCP-элемент — постер
или обложка кейса, то есть изображение; на боевом хостинге с CDN и HTTP/2
значение будет заметно ниже. Для сравнения: тот же контент на desktop-профиле
даёт LCP 0.7 с.

### Размер бандла

Крупнейшие клиентские чанки после сборки (несжатые):

| Размер | Что это |
| --- | --- |
| ~1074 KB | Админка Payload (грузится только на `/admin`) |
| ~571 KB | React + рантайм Next |
| ~530 KB | three.js (грузится только когда сцена запускается) |

На публичных страницах, кроме главной, three.js не загружается вовсе.

## Что сделано для производительности

* Server Components по умолчанию; `'use client'` у шести файлов, каждый обоснован.
* Изображения: Payload генерирует 6 размеров и конвертирует в WebP, `next/image`
  отдаёт AVIF/WebP, у каждого изображения обязательный `sizes` и фиксированный
  `aspect-ratio` (отсюда CLS = 0).
* Шрифты самохостятся через `next/font` с `display: swap` и метриками фоллбэка.
* Кеширование: `unstable_cache` с тегами, сброс хуками CMS при публикации.
* Страницы кейсов пререндерятся (`generateStaticParams`).
* Нет сторонних render-blocking скриптов; аналитика подключается только при
  заданном идентификаторе и стратегией `afterInteractive`.
* Cookie-баннера нет (у трёх из семи референсов он давал сдвиг вёрстки).
* Видео: `preload="none"`, обязательный постер, воспроизведение только в вьюпорте.

## Как повторить измерение

```bash
pnpm build
pnpm start                       # в отдельном терминале
node scripts/lighthouse-audit.mjs
```

Сводка выводится в консоль и в `research/lighthouse/summary.json`.

> Замеряйте на сборке, где `NEXT_PUBLIC_SITE_URL` совпадает с адресом, по
> которому открывается сайт. При несовпадении `robots.txt` запрещает индексацию
> (правильное поведение для не-production окружения), и категория SEO падает
> до 69 — это артефакт окружения, а не проблема сайта.

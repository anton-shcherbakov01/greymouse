# Технические решения

Формат: решение → контекст → почему так → что отвергли → последствия.
Даты не проставляются: все решения приняты при первичной сборке проекта.

---

## 1. Next.js 16.3.0 + Payload 3.87.0 в одном приложении

**Контекст.** Нужны публичный сайт и админка с одним деплоем.

**Почему так.** Проверена официальная таблица совместимости через peerDependencies
пакета `@payloadcms/next@3.87.0`:

```
next: '>=15.2.9 <15.3.0 || >=15.3.9 <15.4.0 || >=15.4.11 <15.5.0 || >=16.2.6 <17.0.0'
```

Next 16.3.0 попадает в поддерживаемый диапазон. React 19.2.8 удовлетворяет
peer-требованиям и Next, и Payload. Версии не выбирались «последние вслепую» —
диапазон проверен до установки.

**Отвергли.** Отдельная headless CMS (Strapi/Directus) + отдельный фронтенд: два
деплоя, две базы, две системы авторизации на проект такого размера — избыточно.

**Последствия.** Payload монтируется в route group `(payload)`, публичный сайт — в
`(frontend)`. Общие только конфиг и типы.

## 2. PostgreSQL, а не MongoDB

**Почему так.** Реляционные связи (кейсы ↔ услуги ↔ категории ↔ команда) выражаются
естественно; `@payloadcms/db-postgres` даёт миграции, которые можно версионировать
и прогонять в CI. Управляемый Postgres доступен у любого хостинга.

**Последствия.** В development включён `push: true` (схема синхронизируется
автоматически), в production — только миграции. Разграничение по `NODE_ENV` в
`src/payload.config.ts`.

---

## 3. Аутентификация — только Payload, без NextAuth

**Почему так.** В админку ходят два-три человека. Payload auth уже даёт JWT в
httpOnly-cookie, блокировку после 8 неудачных попыток, `maxLoginAttempts`,
`lockTime`, ролевую модель. Второй слой авторизации ничего не добавляет.

**Отвергли.** NextAuth/Auth.js — прямо запрещён контрактом при отсутствии
необходимости, и необходимости нет.

**Последствия.** Публичного логина на сайте нет. Роли `admin` и `editor` заданы
полем `role` в коллекции `users` с ограничением доступа на уровне поля.

---

## 4. Чистый three.js вместо React Three Fiber + Drei

**Почему так.** В проекте **одна** сцена. R3F добавляет реконсилятор и обвязку,
Drei — ещё больше, и всё это попадает в клиентский бандл ради одного canvas.
Императивный код three.js здесь короче декларативного и даёт прямой контроль над
тем, что критично: ограничение DPR, остановка цикла по `IntersectionObserver` и
`visibilitychange`, обработка `webglcontextlost`, снижение качества на мобильных.

Дополнительный аргумент из исследования: только 2 из 7 референсов вообще
используют WebGL, а Bravoure получает ощущение трёхмерности статичным рендером —
то есть тяжёлая 3D-обвязка не является отраслевой нормой.

**Отвергли.** `@react-three/fiber` + `@react-three/drei` (~200 KB gzip сверх three.js).

**Последствия.** Сцена изолирована в `src/features/hero-scene/`, грузится через
`next/dynamic` с `ssr: false`.

---

## 5. Motion (`motion@12`) как единственный motion-инструмент, и то ограниченно

**Почему так.** Контракт требует выбрать один инструмент. Взят `motion` (Motion for
React), но применяется **только** там, где CSS объективно не справляется:
`AnimatePresence` для мобильного меню и для смены выдачи фильтров.

Все reveal-анимации сделаны на CSS-переходах + `IntersectionObserver`: это дешевле
по JS и лучше для доступности. Пружинная кривая описана CSS-функцией `linear()` —
приём взят из разбора gravity.nl.

Взята ветка `12.x`, а не только что вышедшая `13.0.0`: на момент сборки 13.x не
имеет истории эксплуатации.

**Отвергли.** GSAP (лицензия + вес ради нескольких эффектов), Lenis
(scroll hijacking, вред доступности — 5 из 7 референсов обходятся нативным
скроллом), одновременное использование GSAP и Framer Motion.

---

## 6. Tailwind CSS v4 + CSS-переменные для токенов

**Почему так.** Tailwind v4 читает токены прямо из CSS через `@theme`, поэтому
дизайн-токены живут в одном месте (`src/styles/tokens.css`) и доступны как утилитам,
так и обычному CSS (например, шейдерам и inline-стилям сцены).

**Важно.** Tailwind импортируется **только** в layout публичного сайта. В
`(payload)` он не попадает, поэтому preflight не ломает стили админки.

---

## 7. Slug латиницей с транслитерацией кириллицы

**Почему так.** Названия кейсов на русском. Кириллица в URL превращается в
percent-encoding и нечитаема в выдаче и в аналитике. Хук `beforeValidate`
транслитерирует название в латиницу; поле остаётся редактируемым, есть валидация
формата и уникальность на уровне БД.

---

## 8. IDN-домен: punycode в canonical, unicode для человека

**Почему так.** `сераямышь.рф` в атрибутах `href`/`content` разные парсеры
обрабатывают по-разному. `src/lib/site.ts` нормализует `NEXT_PUBLIC_SITE_URL`
через `new URL()`, который сам приводит хост к punycode
(`xn--80apaghdkxi3f.xn--p1ai`). Именно эта форма уходит в canonical, sitemap,
OG и structured data. Unicode-форма используется только как видимый текст.

**Последствия.** Адрес задан ровно в одной переменной окружения; в коде он не
продублирован ни разу.

---

## 9. Отказ от scheduled publish

**Контекст.** Payload умеет отложенную публикацию, но она требует включённой
очереди задач (`payload-jobs`) и внешнего планировщика (cron/autorun).

**Почему так.** Для студии с несколькими кейсами в год это лишний движущийся
элемент в проде. Draft/publish workflow, автосохранение черновиков и предпросмотр
реализованы полностью.

**Как включить, если понадобится.** Добавить `schedulePublish: true` в
`versions.drafts` и настроить обработчик очереди — см. `docs/deployment.md`.

---

## 10. Заявки формы пишутся в БД, а не отправляются письмом по умолчанию

**Почему так.** SMTP-доступ не был предоставлен. Заявка всегда сохраняется в
коллекцию `enquiries` (создание доступно только серверному экшену через
`overrideAccess`, публичного `create` нет). Если заданы `SMTP_*` и
`CONTACT_NOTIFY_EMAIL`, дополнительно уходит письмо.

**Последствия.** Форма работает сразу после деплоя, ничего не теряется.

---

## 11. Защита формы: honeypot + временная метка + rate limit в памяти процесса

**Почему так.** Внешние капчи (reCAPTCHA/Turnstile) — сторонний render-blocking
скрипт и передача данных посетителя третьей стороне без запроса владельца.
Реализованы: скрытое поле-ловушка, проверка минимального времени заполнения формы,
ограничение частоты по IP.

**Ограничение, которое нужно знать.** Счётчик частоты живёт в памяти процесса. При
нескольких репликах лимит применяется по каждой реплике отдельно. Для нескольких
реплик нужен общий Redis — отмечено в `docs/deployment.md`.

---

## 12. Свои SVG-иконки вместо библиотеки

**Почему так.** Нужно менее десяти знаков. Библиотека иконок — это лишняя
зависимость и обычно tree-shaking, который работает не полностью.

---

## 13. Vitest только для логики, которую есть смысл тестировать изолированно

**Почему так.** Юнит-тестами покрыты транслитерация slug, нормализация URL сайта,
парсер фильтров списка кейсов, валидация формы (Zod-схема), rate limiter. Рендер
компонентов проверяется E2E — это ближе к реальному поведению и не требует
поддерживать моки Payload.

---

## 14. Исследовательские скрипты остаются в репозитории

**Почему так.** `scripts/research-*.mjs`, `scripts/proxy-relay.mjs` и
`scripts/tls-terminating-relay.mjs` документируют, **как** получены выводы в
`docs/reference-research.md`. Они не участвуют в сборке приложения (исключены из
`tsconfig` и `.dockerignore`) и не тянут runtime-зависимостей.
